## 1. 产品细节

### 1.1 用户故事
- **US-1（自然语言建任务）**：分析组长输入「每天早上 9 点汇总昨日各渠道销售额，发送到飞书群」，系统解析为可编辑的「待确认任务」，确认后定时执行并向飞书群推送执行摘要（图表推送属 R3 可选能力）。
- **US-2（参数化 SQL）**：分析师在 SQL 里写 `WHERE day >= '${yesterday}'`，每次运行自动注入昨日日期，无需每天手改 SQL。
- **US-3（失败告警）**：定时 SQL 执行失败或超时，自动向绑定渠道发送失败原因（脱敏），用户无须登录后台查看。
- **US-4（对话结果推送）**：在对话里完成一次分析后，手动把「结论摘要」推送到飞书/企微/邮箱（**本期仅纯文本**；图表/附件推送与后台图表同属 R3，后置）。

### 1.2 功能范围（In / Out）
**In（本期）**
- Automation 管理：列表 / 表单创建 / 自然语言解析创建（二次确认）/ 编辑 / 启停 / 立即运行 / 删除 / 运行历史。
- 动作：`sql_report`（单条 SELECT + 可选图表）。预留 action 扩展位（export / webhook，本期只留枚举不实现）。
- SQL 参数：占位符注入（内置变量 + 用户变量）。
- 调度：cron 表达式（5 段），daily/weekly/monthly 兼容映射。
- 通知渠道：飞书 / 企微 / 钉钉 webhook + 邮件 SMTP；配置 CRUD / 测试 / 启用。
- 通知触发：Automation 成功/失败；对话结果主动推送（`POST /api/notifications/send`）。
- 发送记录（`notification_logs`）审计留存。

**Out（明确不做）**
- 不做邮件收件（inbox）；不做飞书/企微/钉钉的回复/交互回调。
- 不做跨用户/团队共享渠道（渠道仅归属单用户）。
- 不做 cron 多时区自由选择（本期固定 `Asia/Shanghai`，字段预留 timezone）。
- **不做 automation 运行结果导出**（结果仅存 JSONB 快照，供「历史」页 table/chart 查看；导出复用现有 Export 能力属后续功能）。
- `scheduled_reports` 既有能力保持不动，前端主流程改用 `automations`；旧报告页仍可访问但不作为主入口（渲染时注明「老版定时报告」）。

### 1.3 产品规则 / 约束
1. **二次确认强约束**：自然语言创建必须经「解析 → 展示待确认 JSON → 用户点确认」三步，任何一步缺失不得落库。
2. **只读强约束**：Automation 的 `sql_report` 只允许单条 SELECT（复用 `sql_kind` 判定）；保存与每次执行都校验。
3. **参数求值失败即 failed**：占位符缺值/类型错不静默，置 failed 并（若绑定）发失败通知。
4. **历史裁剪**：每 automation 保留最近 50 条 `automation_runs`（对齐现有 `RUN_HISTORY_KEEP=50`）。
5. **运行超时**：单次执行 60s（对齐 `RUN_TIMEOUT_SECONDS`）。
6. **并发防重**：领取任务时立即推进 `next_run_at`，杜绝调度 tick 重复触发（对齐现有 `refresh_next_run` 领取语义）。
7. **通知失败不阻塞主流程**：通知仅记 `notification_logs` failed，不影响 SQL 结果与运行历史。
8. **渠道密钥脱敏**：config 返回全掩码 `******`，更新留空=不改。
9. **通知上限**：单渠道发送频率控制（默认策略见 §5.5，防 webhook 被滥用刷屏）。
10. **数据源必须显式绑定**：定时任务保存时须携带并校验归属的 `params.datasource_id`，**不允许 LLM 猜测**；未绑定仅作「用默认源」兜底但不推荐（见 §2.6）。
11. **单触发单渠道（MVP 范围）**：on_success / on_failure 各绑定 1 个渠道；需同时推多个目标（如邮件+飞书）本期不做，可后续扩展「渠道组」。

### 1.4 空态 / 加载 / 边界文案（对齐现有 UI 风格）
- Automation 列表空态：图标 + 「暂无定时任务，点右上角「新建」创建第一个自动查询」。
- 通知渠道空态：「暂无通知渠道，至少添加一个飞书/企微/钉钉群机器人或邮箱才能接收推送」。
- parse 解析失败：`无法解析该描述，请调整措辞或使用表单手动创建`，下方给「表单模式」快捷入口。
- 列表加载失败：错误条 + 「重试」。
- 立即运行：按钮变「运行中…」（同现有 `runningId` 状态）。

### 2.3 参数注入（SQL 参数化）
**语法（契约）**
- SQL 内占位符 `${var}`；变量名 `[A-Za-z_][A-Za-z0-9_]*`。字符串型需在 SQL 里自带引号（`'${yesterday}'`），引擎不做补引号，避免歧义。
- 关键设计（R5）：**求值结果总按字符串**替换；是否加引号由 SQL 作者决定。数值型若作者加了引号，由 DB 隐式转换。

**取值层级（先用户变量，后内置变量兜底，同名覆盖内置）**
1. `params.variable_defaults`（JSONB，用户自定义固定值）。
2. 内置变量（运行时按当前时刻求值）：
   - `today` / `yesterday` → `YYYY-MM-DD`
   - `this_month_start` / `this_month_end` / `last_month_start` / `last_month_end` → `YYYY-MM-DD`
   - `now` → `YYYY-MM-DD HH:MM:SS`
   - `date` → 同 `today`（别名）

**实现（`AutomationService._resolve_sql`）**
```python
_VAR_RE = re.compile(r"\$\{([A-Za-z_][A-Za-z0-9_]*)\}")

BUILTIN_VARS: dict[str, Callable[[datetime], str]] = {
    "today": lambda d: d.strftime("%Y-%m-%d"),
    "yesterday": lambda d: (d - timedelta(days=1)).strftime("%Y-%m-%d"),
    "this_month_start": lambda d: d.replace(day=1).strftime("%Y-%m-%d"),
    "this_month_end": lambda d: (d.replace(year=d.year + (d.month // 12), month=d.month % 12 + 1, day=1) - timedelta(days=1)).strftime("%Y-%m-%d"),
    "last_month_start": lambda d: (d.replace(day=1) - timedelta(days=1)).replace(day=1).strftime("%Y-%m-%d"),
    "last_month_end": lambda d: (d.replace(day=1) - timedelta(days=1)).strftime("%Y-%m-%d"),
    "now": lambda d: d.strftime("%Y-%m-%d %H:%M:%S"),
    "date": lambda d: d.strftime("%Y-%m-%d"),  # today 别名
}

def _resolve_sql(sql: str, defaults: dict, run_at: datetime) -> tuple[str, list[str]]:
    missing: list[str] = []
    resolved = {}
    for name in _VAR_RE.findall(sql):
        if name in defaults:
            resolved[name] = str(defaults[name])
        elif name in BUILTIN_VARS:
            resolved[name] = BUILTIN_VARS[name](run_at)
        else:
            missing.append(name)
    if missing:
        raise ValueError(f"变量未定义: {missing}")  # 无占位符时正常返回
    return _VAR_RE.sub(lambda m: resolved[m.group(1)], sql), sorted(missing)
```
- 缺失变量 → ValueError → run 置 failed + 触发失败通知。无任何占位符 → 原样执行（向后兼容）。

### 2.4 调度（croniter）
- `AutomationService.compute_next`: `croniter(cron_expression, now).get_next(datetime)`；保存/更新/领取都重算 `next_run_at`。
- **croniter 遵循标准 cron DOW 语义**（0 和 7 均=周日，1=周一…6=周六），**与 python `weekday()`（0=周一…6=周日）不一致**。因此「周一→周日」内部统一用 python 语义存 `dow`，生成 cron 表达式时必须转换：`cron_dow = (python_dow + 1) % 7`。
- 兼容映射（供表单 & 解析器生成，**必须转换 DOW**）：
  - daily → `"min hour * * *"`
  - weekly(python_dow) → `"min hour * * {cron_dow}"`，其中 `cron_dow = (python_dow + 1) % 7`
  - monthly(dom) → `"min hour dom * *"`
- **映射等价性必须有单测**：覆盖「每周一」「每月 31 日（小月顺延）」与老 `compute_next_run` 的到期结果一致；否则 weekly 任务会整体错位一星期（阻塞性缺陷）。
- cron 校验：创建/更新时用 `croniter.is_valid` 校验，非法 400；字符集白名单（`* / 0-9 , -` 与空格分隔）防注入。**明确收窄**：不支持 cron 扩展语法 `? # L W`（croniter 虽支持，但白名单已排除，避免语义复杂化与注入面）；`croniter.is_valid` 兜底。

### 2.5 调度器扩展（复用现有 Scheduler）
`scheduler.py` 保持 `TICK_SECONDS=30`，在 `_run_due_reports` 旁新增 `_run_due_automations`：扫 `automations` 表 `enabled=true AND next_run_at<=now`，逐个 `asyncio.create_task(AutomationService.run(automation_id))`，与报告互不影响。

### 2.6 SQL 执行与图表（复用现有能力）
- `AutomationService.run` 内调用：`SqlEngine().execute(user_id=automation.user_id, session_id=str(automation.id), sql=resolved_sql, datasource_id=params.get('datasource_id') or None)`。
- **数据源选择（关键产品点）**：
  - **必须显式选定数据源**。定时任务保存时必须携带 `params.datasource_id`，服务端校验归属且**强制非空**（`ds.user_id == current_user.id`）。**注意**：现有 [reports._validate_datasource_id](file:///Users/umlink/chat-data-pilot-agent/backend/app/api/reports.py#L54-L63) **允许空值**（报告可回退默认源，[create_report](file:///Users/umlink/chat-data-pilot-agent/backend/app/api/reports.py#L119-L120) 空则置 None），不能直接复用；Automation 需**自己的必填校验**（复用其「存在性 + 归属」判定逻辑，但空串直接 400「请选择数据源」）。不存在/非本人 400。
  - **为何不让 LLM 猜**：`datasource_id` 归属校验只有服务端能做，LLM 无法知道当前用户拥有哪些数据源，凭名称猜会跨数据源/猜错；且 SQL 是针对生成时看到的 schema 构造的，必须绑定到该数据源，否则执行会错。因此数据源 id 一律来自**用户显式选择**（表单下拉 / 自然语言解析后的确认卡，见 §3.2）。
  - **回退兜底**：若 `datasource_id` 为空，`SqlEngine._find_datasource` 会自动取用户首个数据源（[sql_engine.py](file:///Users/umlink/chat-data-pilot-agent/backend/app/services/sql_engine.py#L326-L343)）。视为「**未绑定数据源、用默认**」，仅作兼容兜底，**不推荐**——因为 LLM 生成的 SQL 若与默认源 schema 不符会执行失败。产品上建议表单层强制让用户选择。
  - SQL 校验：**保存与每次执行都走 `sql_kind` 只读判定（与 `report_service` 一致）**；执行时**不做额外 schema 校验**（schema 匹配在生成阶段由「LLM 看到所选数据源 schema 后构造 SQL」保证，对齐报告现状；执行期只保证 select-only，避免新增复杂度）。
- **max_rows 一致性（修正：与报告现状对齐，不引入行为变更）**：现有 [report_service._execute_report_sql](file:///Users/umlink/chat-data-pilot-agent/backend/app/services/report_service.py#L120-L133) 调 `SqlEngine.execute` **未传 `max_rows`**，使用引擎硬编码默认 `1000`（[sql_engine.execute](file:///Users/umlink/chat-data-pilot-agent/backend/app/services/sql_engine.py#L246)），与 `system.query.max_query_rows` 默认值 1000 恰好相同，但**报告并未真正读取该配置**（「行数上限同系统配置」是注释转述的巧合）。**Automation 本期与报告完全对齐：也不传 `max_rows`，用引擎默认 1000**，两处行为一致、零额外改动。「统一显式读配置」列为可选优化，需单独决策（会改动 report_service），不并入本期。
- `session_id=str(automation.id)` 用于 att_ 路由（与 `report_service` 一致，避免与真实会话混淆）。
- 图表：`params.chart_config` 存在时 `asyncio.to_thread(build_chart, table, chart_type, dimension, measures, title)`，返回 `{table, chart?}` 存入 result。
- 超时 `asyncio.wait_for(..., timeout=60)` → TimeoutError 置 failed。
- 错误收敛：`automation_service` 内**等价实现** `_sanitize_error`（复用 `SqlNeedsConfirmation.reason` / 截断 500 的语义）。**边界（防过度设计）**：不抽取公共共享函数、不重构 `report_service`——`AutomationService` 独立实现（语义对齐即可），避免改动已交付代码引入回归；报告与自动化的执行链路不抽象复用（两处各自收敛，各自裁剪历史，仅常量一致 60s/50 条）。

### 2.8 自然语言解析（`POST /api/automations/parse`）
- 非流式：`provider.chat(messages, temperature=0, max_tokens)`，系统提示要求在严格 JSON 内返回 `{name, params:{sql_text,chart_config,variable_defaults}, schedule:{type,time,dow,dom}, notification:{on_success,on_failure}}`。
- **cron 由后端生成，LLM 只输出 schedule 语义结构（重要修正）**：cron DOW 语义（0/7=周日，1=周一）与常识（周一=1）相反，若让 LLM 直接编 `cron_expression` 极易把「每周一」写成错误 DOW。因此 parse 产物中 LLM **只输出 `schedule:{type: daily|weekly|monthly, time:HH:MM, dow?:0-6(python 语义 0=周一), dom?:1-31}`**，后端用 §2.4 映射（含 `cron_dow=(python_dow+1)%7` 转换）生成 cron 并校验。create/update 接口则**直接接受 `cron_expression`**（专家表单场景，后端 croniter 校验）。
- **LLM 不猜数据源（parse 必填 + 确认卡锁定，修正）**：`params.datasource_id` 由用户显式选择、LLM **不允许**输出（归属只有服务端能校验，LLM 会猜错/跨源）。**parse 入参 `datasource_id` 必填**——LLM 必须基于所选数据源的 schema 生成 SQL，无 schema 会幻觉列名；前端在点「智能解析」前强制选择（默认当前会话/最近使用的数据源）。解析产物不含 `datasource_id`，确认卡**锁定 parse 所用数据源**：用户改数据源须重新 parse（原「确认卡可改、以确认为准」允许改后不重解析，会造成 SQL 与目标源 schema 错配，属遗漏）。
- 二选一工具 lex：优先 `chat` + JSON 模式；若 Provider 支持 tool calling（`chat_with_tools`）则用单工具 `parse_automation` 强制 structured（对齐 Block 协议第 4 章「支持工具调用优先工具、否则降级严格 JSON」）。
- **LLM 截断 / 非严格 JSON 兜底**：复用上下文压缩的 JSON 修复思路（补引号、去尾部逗号、括号栈修复），失败则返回 400 + `无法解析` + 提示改表单。
- 解析结果含 `readable` 摘要（`每天 09:00 · 汇总昨日各渠道销售额`，**不含数据源名**，因 LLM 不猜测数据源），供前端确认卡片展示。
- **不落库**：parse 是只读，返回待确认结构（AutomationDraft 内 **cron_expression 已由后端按 §2.4 生成并校验**，可直接确认提交）；确认走 `POST /api/automations`（**直接提交解析结果 body**，即 AutomationCreate 结构；不引入 `parsed: true` 标记，与 §7 契约一致）。

### 2.9 安全
- 全部按 id 取实体校验归属（当前用户），对齐 `_get_owned_report` 写法。
- 渠道密钥 `encrypt_secret`（**含 `webhook_url`**，URL 内嵌鉴权 token/key/access_token，见 §2.1 字段契约）；对外掩码；更新 `upsert_secret` 保留掩码与旧密文（`notification_channels` 走现有 `security.py`）。
- 通知发送日志禁止含密钥；webhook URL 掩码。
- cron 表达式白名单校验字符集防御注入（仅 `* / 0-9 , -` 与字段分隔，`croniter.is_valid` 兜底）。
- **渠道删除后的引用**：`automations.notification` 内嵌 `channel_id` 无外键，渠道删除不会级联清理。删除渠道时须一并扫描、置空引用该渠道的 automation 的通知绑定（或发送时渠道不存在则跳过并记 `notification_logs` failed「渠道已删除」）；二选一在实现时定，推荐**删除时解绑**避免每次执行都空转。
- **渠道停用（enabled=false）时的绑定行为（补全，此前遗漏）**：与「删除」不同，**停用是临时状态**——自动化绑定**保留**（恢复启用后自动恢复）；运行时若绑定渠道已停用，**静默跳过发送、不写 notification_logs**（用户主动停用，不刷 failed 日志）。交互上在停用渠道时提示「停用后自动化将不再向该渠道发送，恢复启用后自动恢复」。
- **automation 保存时校验 notification 内 channel_id**：创建/更新 automation 时，`notification.on_success.channel_id` / `on_failure.channel_id` 若提供，必须**存在且属于当前用户**（否则 400）；**不要求必须 enabled**（允许绑定后再停用渠道）。
- **CRUD 审计日志（补全，对齐现有 reports）**：`automations` 与 `notification_channels` 的创建/更新/删除均记 `audit` 类日志（`LogService.write_log`，带 `user/resource/action`，对齐 [api/reports.py](file:///Users/umlink/chat-data-pilot-agent/backend/app/api/reports.py#L162-L165) 的既有做法）。
- **变量注入读取面（明确边界）**：`variable_defaults` 为用户可控，注入后仅作值替换、SQL 结构固定，且替换后仍走 `sql_kind` 只读判定——因此**无写危害**；但用户变量可放大查询读取范围（如 `'${v}'` 注入使条件失效读全表）。属用户自有任务的合理行为，文档明示即可。
- **parse 的 LLM 失败返回码**：模型未配置 / Provider 网络不可用时捕获 `LLMError`，返回 400 + 可读「智能解析不可用，请检查 LLM 配置或改用表单」；不得落到 500 崩溃。
- **执行期删除并发**：`AutomationService.run` 领取后若 automation 已被删除，对齐 `run_report` 的「报告已删除→运行记录置 failed」，不得在已删对象上写属性。

## 5. 关键实现决策与约束

### 5.1 错误处理（对齐基线）
- 统一信封 `{code, data, message}`；业务错误 `HTTPException(4xx, 中文)` 由全局 handler 转换。
- SQL/运行错误只落 `runs.error`（脱敏），不返回到信封外层。
- 通知发送失败：logged，`/api/notifications/logs` 可查 status=failed。

### 5.2 越权
- 所有按 id 取 automation / channel / run 必须校验 `user_id == current_user.id`，不存在/非本人一律 404。

### 5.3 时钟与时区
- cron 计算与内置变量统一用 `Asia/Shanghai`（`zoneinfo.ZoneInfo('Asia/Shanghai')`），时间戳落库存 UTC（`timezone.utc`），`automations.timezone` 字段预留但本期固定值。
- **与现有报告对齐（阻塞性一致性）**：现有 [report_service.compute_next_run](file:///Users/umlink/chat-data-pilot-agent/backend/app/services/report_service.py#L44-L92) 用**服务器本地时区** `datetime.now().astimezone()` 解释 `HH:MM`，而 automation 固定 `Asia/Shanghai`。若部署服务器非上海时区，两种任务的「到期时刻」会错位，用户不可接受。**实现前须确认部署服务器时区 = `Asia/Shanghai`（或同一时间），并加单测**：同一 `next_run_at` 换算到上海时区与老报告语义一致。
- croniter `now` 传 `Asia/Shanghai` aware datetime；python weekday 与 cron DOW 差异由 §2.4 转换公式 + 单测锁定。

### 5.4 幂等 / 并发
- 调度领取即推进 `next_run_at` 防重；若进程双开调度器，用现有「领取即推进」即可（重复 tick 会查空）。
- 立即运行 `POST /{id}/run` 同步等待，与调度并发时靠推进 next_run_at 兜底。

### 5.5 通知频控（防刷屏）
- **单层限流（简化，防过度设计）**：单 channel 每 1 分钟最多 1 条失败告警；成功摘要不额外限流但记录。频控计数存 **Redis**（key `notify:freq:{channel_id}:{window}`，基于现有 `redis.asyncio`），不用 DB 行级计数避免写放大。
- **不引入全局阈值配置项**：曾设 `system.notification.max_fail_per_min`（全局层），与「单 channel 每 1 分钟 1 条」语义重叠、且需在 `DEFAULT_CONFIGS` 注册（否则 `set_many` 抛 `KeyError`）——经评估属**过度设计**，砍掉。仅保留单 channel 层即可满足防刷屏；如需调频率，未来再加配置。
- **notification_logs 裁剪（补全，此前遗漏）**：发送记录长期增长，须裁剪。策略：**每用户保留最近 500 条**，超出删最旧（对齐 `automation_runs` 保留 50 的裁剪思路，但发送记录量大，取 500）；在写入时顺手清理（低频、量小），不引入独立后台任务。

### 5.6 与现有「定时报告」的关系
- 前端主流程改为 Automation；`scheduled_reports` 的 service/API/scheduler 分支**保留不动**，作为内部兼容与过渡，避免破坏已交付数据。
- 迁移策略：未来如需合并，`scheduled_reports` → `automations(action=sql_report, cron=map(...))` 一次性迁移 + 校验，本期不做。

|---|---|---|
| croniter 与老 `compute_next_run` 语义不一致 | 用户已有报告到期时间变化 | §2.4 映射（含 DOW 转换公式 ` (python_dow+1)%7`）单测锁定 daily=每天 / weekly=含 dow / monthly=含 dom；迁移不触碰 scheduled_reports |
| croniter DOW 与 python weekday 语义错位 | weekly 任务整体错位一星期 | 周一→周日的 cron 表达式必须 `cron_dow=(python_dow+1)%7`，单测覆盖每一工作日 |
| 服务器时区非上海导致两种任务到期错位 | 用户困惑、部分任务时间不符 | §5.3：实现前确认部署时区=上海或同一，加 next_run 换算单测 |
| webhook 外网不可达/慢 | 通知卡主流程 | 独立异步 + 8s 超时 + 失败只记 log，绝不阻塞 SQL 结果 |
| 后台图表推送（R3） | 本期无静态 URL，「图表链接」伪资源 | 首期只发纯文本摘要+失败原因；图表推送待 R3（服务端 PNG/静态路由）|
| LLM 解析出非目标 JSON / 幻觉 | parse 出错或建错 cron | 严格 JSON/tool + post-validate（cron sql 归属全部校验）+ 必须二次确认 + LLMError 兜底 400 |
| 钉钉加签密钥泄露 | 机器人被滥用 | secret 加密存储、禁日志、掩码回显；IP 白名单可配额 |
| 用户变量放大查询读取范围 | 读全表/越读取 | 属用户自有任务合理行为，文档明示；仍只读、无写危害（§2.9）|
| 渠道删除后 automation 残留引用 | 发送空转/静默失败 | 删除渠道时扫描解绑 automation 通知引用（§2.9）|

```sql
CREATE TABLE automations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name VARCHAR(100) NOT NULL,
    description TEXT,
    action VARCHAR(30) NOT NULL,
    params JSONB NOT NULL DEFAULT '{}',
    cron_expression VARCHAR(100) NOT NULL,
    timezone VARCHAR(50) NOT NULL DEFAULT 'Asia/Shanghai',
    enabled BOOLEAN NOT NULL DEFAULT true,
    notification JSONB,
    last_run_at TIMESTAMPTZ,
    last_status VARCHAR(20),
    next_run_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ix_automations_due ON automations (enabled, next_run_at);
CREATE INDEX ix_automations_user_created ON automations (user_id, created_at);

CREATE TABLE automation_runs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    automation_id UUID NOT NULL REFERENCES automations(id) ON DELETE CASCADE,
    status VARCHAR(20) NOT NULL,
    started_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at TIMESTAMPTZ,
    duration_ms INTEGER,
    error TEXT,
    params JSONB,
    result JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ix_automation_runs_automation_started ON automation_runs (automation_id, started_at);

CREATE TABLE notification_channels (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    provider VARCHAR(20) NOT NULL,
    name VARCHAR(100) NOT NULL,
    config JSONB NOT NULL DEFAULT '{}',
    enabled BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ix_notification_channels_user_created ON notification_channels (user_id, created_at);

CREATE TABLE notification_logs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    channel_id UUID REFERENCES notification_channels(id) ON DELETE SET NULL,
    subject VARCHAR(500),
    body TEXT,
    attachment_json JSONB,
    status VARCHAR(20) NOT NULL,
    error TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ix_notification_logs_user_created ON notification_logs (user_id, created_at);
```

## 附录 B：各渠道载荷要点
- 飞书 text：`{"msg_type":"text","content":{"text":…}}`
- 飞书 interactive（文本卡片，不做图表链接）：`{"msg_type":"interactive","card":{"header":{"title":{"content":…}},"elements":[{"tag":"div","text":{"content":…}}]}}`
- 企微 markdown：`{"msgtype":"markdown","markdown":{"content":…}}`
- 钉钉 text / markdown（加签）：`{"timestamp":…,"sign":…,"msgtype":"text","text":{"content":…}}`
- 邮件：`MIMEText(body, "html", "utf-8")`（HTML 正文须显式指定 subtype，默认 text/plain 会乱码），SMTP `starttls`/`ssl` 按 config.use_tls；**本期无附件**（MIMEImage 图表附件待 R3）。

> 本期所有渠道只发**文本/卡片文本**（摘要 + 结果行数 + 耗时 + 失败原因），不含图表附件。图表演示依赖 R3（服务端 PNG / 静态链接）。
